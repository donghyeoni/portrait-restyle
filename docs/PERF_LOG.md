# 성능 로그 — 카드 생성 시간

개발 GPU 서버(TLJH, L40S device 1 할당)에서 잰 생성 시간 기록. 방식이 바뀔 때마다 한 행씩 추가한다.
숫자는 조건이 다르면 못 비교하므로 각 측정의 **범위(무엇을 포함했나)** 를 함께 적는다.

## 측정 환경

| 항목 | 값 |
|---|---|
| GPU | L40S 46GB 중 device 1 (ComfyUI 24GB + GPU 서비스 상주). device 0·2·3 은 미사용(우리 할당 아님) |
| CPU | 96 스레드 |
| 엔진 | 직업·12지신 inswapper(CPU), 컨셉 PuLID·웹툰 Kontext(FLUX, GPU), 누끼 BiRefNet-portrait |
| 산출물 | IMAGE·CUTOUT·THUMBNAIL (webp), 관리자 SUBJECT_MASK(png) |
| 원본 | `data/input/woman/001.png` (얼굴 검출 1명) |

**시간의 두 종류.** ① 아이템 생성 시간 = 생성+누끼+인코딩(계산만). ② 아이템 총시간 = ① + S3 다운로드·업로드 3건 + HMAC 콜백 + 하트비트(큐 경유 실측). 아래 표마다 어느 쪽인지 표시한다.

## 5. 동시성 벤치 — 워커 1 vs 3 (2026-09-10)

배치 23장(직업 8·12지신 12·컨셉 2·웹툰 1)을 스레드 풀로 동시 실행. **아이템 생성 시간**(큐·콜백·S3 제외), 사전 마스크 적용 상태, GPU 아이템은 실제 서비스(8080) 호출.
| 워커 | 전체 소요(makespan) | 첫 완료 | CPU 20장 완료 | GPU 3장 (컨셉/컨셉/웹툰) |
|---|---|---|---|---|
| 1 (현재) | 92.2s | 13.5s | 92.2s | 13.5 / 13.6 / 37.6s |
| 3 | **71.4s** | **1.9s** | 28.7s | 20.3 / 26.6 / 54.3s (서비스 대기 포함) |

N=1 은 전부 직렬이라 makespan = CPU 20장(장당 1.38s = 27.6s) + GPU 3장(64.6s). CPU 20장이 GPU 뒤에서 순서를 기다려 92초.
N=3 은 CPU 20장이 GPU 그림 시간 밑에 숨어(28.7초에 다 끝남) makespan 이 71초로 −23%, 첫 카드는 1.9초로 급감(직업 아이템이 바로 나옴).
GPU 개별 시간이 늘어 보이는 건(13.5→20.3 등) 세 요청이 서비스 동시성 1 에 걸려 대기하기 때문 — 순수 그림 생성 합은 그대로다.

**해석.** 워커 병렬은 CPU 20장을 공짜로 만들고 첫 카드를 즉시 띄운다. 남은 벽은 **GPU 직렬 약 65~71초**(그림 46초 + 누끼·전송이 서비스 안에서 일부만 겹침).
이 벽을 더 낮추려면: ① 누끼를 GPU 서비스 밖(워커 CPU)으로 빼서 다음 그림과 완전히 겹치기 → 약 48초 예상, ② 스텝 축소(PuLID 22→16·Kontext 20→14, 품질 A/B), ③ webp 무손실→품질95.
GPU 배치(한 번에 여러 장)는 FLUX 가 이미 GPU 를 꽉 채워 이득이 없어 채택 안 함.

측정은 계산만(큐·콜백·S3 제외)이며, 실제 총시간은 아이템당 S3·콜백 몇 초가 더 붙되 워커 3개에서 함께 겹친다. 실서버 총시간은 백엔드 다음 발행 때 워커 로그로 확정한다.

## 6. 실서버 라이브 — 큐 분리 워커 풀 (2026-09-10 16:43~, 발견 측정)

측정 중 서버에 이미 더 나아간 구성이 가동 중임을 확인했다(AI 팀 별도 세팅). 계획의 "워커 병렬"을 **큐 분리 + 워커 풀**로 실현한 것.

| 구성 | 값 |
|---|---|
| 큐 | `motion.ai.generate.item.cpu` (직업·12지신) / `motion.ai.generate.item.gpu` (컨셉·웹툰) 로 분리 발행 |
| CPU 워커 | 4개 (`gpu-worker-cpu-01~04`) — CPU 큐 병렬 소비 |
| GPU 워커 | 1개 (`gpu-worker-gpu-01`, 17:28 기동) — GPU 큐 소비, 직렬(서비스 동시성 1) |
| 코드 | 사전 마스크(`steps/refmask.py`) 반영본 사용 |

**실측 (아이템 총시간, S3·콜백 포함, 33건):**

| 지표 | 값 |
|---|---|
| CPU 아이템 장당 (직업·12지신) | 중앙 2.7s (2.1~3.3s), 첫 건 콜드 20.9s |
| 이전 대비 | 18~24s → 2.7s (사전 마스크 + 큐 분리 병렬) |
| GPU 아이템 | 아직 발행 없음(GPU 큐) — 다음 테스트에서 확인 |

주의로 남길 점: `gpu-worker-cpu-01` 이 두 프로세스로 중복(pid 554097·556323, 같은 WORKER_ID·HTTP 8090). 두 번째는 HTTP 바인딩만 실패하고 소비는 하는 상태 — 클레임 attribution 이 섞일 수 있어 하나로 정리 권장(런타임은 건드리지 않고 보고만).

**요약.** 사용자 1명 CPU 20장이 이전 6분 30초 → 큐 분리 4워커에서 병렬로 수십 초 규모. 남은 벽은 GPU 3장(직렬 ~65초)이며, 5절 벤치가 그 한계를 보여 준다.
GPU 벽을 낮추는 다음 수: ① 누끼를 GPU 서비스 밖으로(→약 48초), ② 스텝 축소 A/B, ③ webp 품질95. (2·3은 품질 확인·백엔드 통보 필요)

## 7. 누끼 CPU 오프로드 배포 후 측정 (2026-09-11)

`GPU_IMAGE_ONLY=true` 배포. GPU 서비스는 그림만 반환, 누끼·인코딩·업로드는 GPU 큐 워커(CPU). GPU device1 메모리 42GB→20GB(누끼 22GB 제거). 사용자 1명 GPU 3장(컨셉2+웹툰1) 측정:

| GPU 큐 워커 | makespan | GPU 유휴 | 비고 |
|---|---|---|---|
| 2개 | 84.5s | 있음 | 두 워커가 CPU 누끼(15~20s) 도는 동안 GPU 놀음 |
| 3개 | 70.5s | **없음** | 웹툰 22s + 컨셉 11.5×2 = GPU 45.6s 연속. 마지막 누끼 25s 가 꼬리 |

핵심: CPU 누끼(BiRefNet, 장당 15~20s)가 그림(컨셉 11.5s)보다 길다. 그래서 GPU 를 계속 그리게 하려면 **워커 3개 이상**이라야 한다(한 워커가 그리는 동안 나머지가 누끼).

| 지표 | 이전(누끼 GPU, 워커1) | 이후(누끼 CPU, 워커3) |
|---|---|---|
| 사용자당 GPU 3장 | ~65s | ~70s (소폭↑) |
| GPU 점유/사용자 | ~65s (그림+누끼) | **~46s (그림만)** |
| 시간당 처리(GPU 1장) | ~55명 | **~78명 (+42%)** |
| device1 메모리 | 42GB | 20GB |

**정리.** 이 변경은 **여러 명 처리량**을 위한 것(그림 전용 GPU → +42%). 단일 사용자 지연은 CPU 누끼가 느려 5초 늘었다. 워커 2개는 부족(GPU 유휴) → **3개 이상 필요**. 22GB 는 그대로 확보.

참고: 22GB 는 모델 크기가 아니라 onnxruntime CUDA 아레나 과할당이었다. BiRefNet 실제 모델은 ~1GB. CPU 에서는 RAM ~1~2GB 로 돌되 15~20초.
